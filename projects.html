PROJECT DETAILS / NETWORK

글로벌 게임회사 IT 인프라 설계 및 구축

01. 프로젝트 개요와 목표

글로벌 게임 서비스를 제공하는 가상의 기업을 대상으로 한국 본사(HQ), 개발센터(DEV), 데이터센터(IDC), 일본 지사(JP)를 포함한 네트워크 인프라를 설계·구축했습니다. 기업의 부서별 네트워크 분리, 사용자 IP 자동 할당, 거점 간 통신 및 서버 접근을 고려한 실습 프로젝트입니다.

주요 수행 범위는 GNS3 기반 본사 네트워크의 설계·구축 및 통신 장애 점검입니다. 다른 거점은 전체 구성 범위에 포함되지만, 모든 구간의 최종 동작을 확인한 것으로 표기하지 않습니다.

02. 담당 업무 및 수행 내용

  • 가상 게임회사 조직 구조를 반영한 네트워크 토폴로지와 부서별 VLAN/IP 계획 수립
  • HQ의 Core–Distribution–Access 3계층 스위치 구성 및 장비 연결
  • 액세스 스위치 포트의 부서별 VLAN 할당과 상위 스위치 Trunk 설정
  • DHCP 서버와 VLAN별 DHCP Relay 구성 및 사용자 단말의 주소 할당 확인
  • 라우터 기본 경로, 내부 라우팅 및 NAT 연동 실습
  • VPCS와 Windows 테스트 PC를 활용한 IP·게이트웨이·ping 점검
  • 장애 발생 시 ARP, 인터페이스 상태, 라우팅 테이블 및 DHCP 흐름 분석

03. 네트워크 설계

전체 구조HQ / DEV / IDC / JP 거점으로 구분한 글로벌 게임회사 인프라
본사 구조Core–Distribution–Access 3-Tier 구조로 장비 역할 분리
부서별 분리VLAN 10~100을 업무 부서에 배정하고, VLAN 110 서버망과 VLAN 199 관리망을 별도로 계획
IP 할당사용자 단말은 DHCP, 주요 서버와 네트워크 장비는 관리 가능한 주소 체계로 구분
테스트 환경전체 인원 규모를 PC 수만큼 복제하지 않고 부서별 대표 VPCS와 Windows PC로 통신 검증

설계 이유: 3계층 구조로 스위치 역할을 분리하고, VLAN을 통해 부서 간 브로드캐스트 영역을 나눴습니다. 대표 단말 방식은 GNS3 실습 환경의 자원 사용을 줄이면서 부서별 IP 할당과 통신 경로를 확인하기 위한 선택입니다.

04. 구현 및 설정 작업

  • VLAN 및 Trunk: 부서별 액세스 포트 VLAN 할당, Distribution·Core 연결 포트의 Trunk 구성
  • DHCP: Rocky Linux 기반 DHCP 서버와 상위 L3 인터페이스의 DHCP Relay 설정, 클라이언트 주소 할당 테스트
  • 라우팅: HQ 라우터와 ISP 방향 연결, 기본 경로 및 내부 경로 점검
  • NAT 및 외부 연결: 외부 구간 연결을 위한 NAT·게이트웨이 구성 실습과 통신 테스트
  • 운영 점검: show ip interface brief, show ip route, show mac-address-table, arp, ping 등으로 상태 확인

05. 문제 발생 및 해결 과정

사례 A · DHCP 주소 미할당

증상: 본사 일부 부서 단말에서 DHCP 주소를 받지 못해 통신이 진행되지 않았습니다.

점검: VLAN 포트 소속, Trunk 연결, DHCP Relay 설정과 DHCP Discover 흐름을 확인했습니다.

조치 및 결과: 연결 및 설정 상태를 재점검해 DHCP 동작을 복구한 기록이 있습니다. 일부 다른 구역의 할당 장애는 당시 추가 확인이 필요했으므로 전체 부서 해결로 표현하지 않습니다.

사례 B · 내부 통신은 되지만 외부 ping 실패

증상: 내부 장비 간 통신은 가능했으나 외부 주소(8.8.8.8)로의 ping이 실패했습니다.

점검: HQ–ISP 연결, 기본 경로, 게이트웨이와 NAT 구성 여부를 확인했습니다.

조치 및 결과: 기본 경로를 재구성하고 내부 ping 성공을 재확인했습니다. 외부 인터넷 통신의 최종 성공은 확인된 자료가 없어 완료로 표기하지 않습니다.

사례 C · ARP incomplete 및 인터페이스 상태 문제

증상: ARP 항목이 incomplete로 표시되거나 연결 인터페이스 상태가 비정상적으로 나타났습니다.

점검: 연결 포트 상태, VLAN 및 상대 장비 인터페이스를 확인했습니다.

조치 및 결과: 관련 인터페이스의 shutdown/no shutdown과 연결 상태 점검 후 통신을 복구한 사례가 있습니다.

06. 테스트 및 검증 결과

확인됨HQ 일부 대표 PC의 DHCP 주소 수신 및 내부 ping 성공
확인됨VLAN/Trunk 구성, 라우팅·인터페이스 상태 출력 기반 점검 수행
부분 확인DHCP 장애 복구, ARP 및 인터페이스 장애 점검 사례
미확인모든 거점 간 종단 간 연결, 외부 인터넷 최종 통신 성공, 전체 서버 서비스 동작

기존 실습 VM 일부가 정리되어 현재 모든 결과를 동일한 환경에서 재검증한 상태는 아닙니다. 검증 캡처와 토폴로지 원본은 확보한 자료를 확인한 뒤 추가할 예정입니다.

07. 프로젝트를 통해 배운 점

네트워크는 단순히 장비를 연결하는 것으로 끝나지 않는다는 점을 배웠습니다. VLAN, DHCP, 라우팅, NAT가 각각 정상이어도 연결 경로 중 하나가 어긋나면 전체 통신이 실패할 수 있었습니다. 그래서 장애가 발생하면 증상부터 확인하고, L2 연결·IP 할당·게이트웨이·라우팅 순으로 원인을 좁히는 점검 방식을 실습했습니다.

CASE STUDY 02 / NETWORK & SECURITY

물류센터·물류 DC 네트워크 및 보안 인프라 구축

프로젝트 형태3인 팀 프로젝트
담당 영역물류센터 · 물류 DC
실습 환경GNS3 · VirtualBox · Linux

01. 업무가 이어지는 인프라 만들기

쇼핑몰 주문이 물류 재고 예약과 출고 작업으로 이어지고, 본사 ERP에서 물류 현황을 조회할 수 있는 환경을 목표로 했습니다. 팀은 본사 ERP, 서비스 DC, 물류 영역으로 역할을 나눴으며, 저는 물류센터의 사용자 네트워크와 물류 DC의 업무 시스템·보안 구역을 맡았습니다.

물류센터는 직원 단말과 사내 DNS·DHCP를 수용하는 3계층 구조로, 물류 DC는 WMS 서비스를 운영하는 Spine–Leaf 구조로 분리했습니다. 서버 간 통신은 API 계약과 전용 키를 기준으로 구분했습니다.

독립된 두 거점, 서로 다른 네트워크 역할

물류센터는 직원·물류 단말과 사내 서비스를 수용하고, 물류 DC는 WMS 업무 서버와 보안·관리 구역을 운영합니다. 두 구성을 각각 나누고 거점 간 연결은 별도로 표시했습니다.

ARCHITECTURE 01

물류센터 · 사용자와 사내 서비스

Core–Distribution–Access, VLAN 40·90, HSRP, DNS·DHCP와 보안 확장 배치를 구분했습니다.

ARCHITECTURE 02

물류 DC · WMS 서비스와 보안 구역

경계 보안, Border Leaf, Spine–Leaf, 6개 서비스 서버와 관리망을 나눴습니다.

ARCHITECTURE 03

거점 간 연결 · VPN과 API

본사 ERP의 VPN 접근, 서비스 DC의 WMS 호출, WMS의 서비스 DC 호출을 방향별로 분리했습니다.

센터 보안 장비 추가는 확장 설계로 표시했습니다. DC의 중앙 로그는 rsyslog 구성이며, 이중 연결은 토폴로지 설계 구조입니다.

02. 팀 역할과 나의 담당 업무

본사 ERP · 팀원 담당

ERP 업무 기능과 본사 네트워크, ERP에서 물류 정보를 조회하는 호출 측 연동

서비스 DC · 팀원 담당

쇼핑몰·주문 서비스와 서비스 API 운영, 물류 API 호출 측 연동

물류 영역 · 직접 담당

센터 네트워크, 물류 DC 서버·보안 구역, WMS 구축, VPN·API 연동 설정, 중앙 로그 수집

  • 센터: LC-CORE1/2, LC-DIST1/2, LC-ACC1~3의 계층 구조와 직원·서버 주소 계획, HSRP·DHCP Relay 구성
  • DC: Border Leaf, Spine, 서비스별 Leaf 배치와 LB·WEB/WAF·WAS·DB·JUMP·로그 서버 구역 설계
  • 서비스: WMS 배포, systemd 서비스 운영, WEB 프록시와 MariaDB 연계, 서버 간 키 설정
  • 보안·운영: pfSense·IPsec VPN 설정, Suricata IDS/IPS 배치, rsyslog 수신과 호스트별 저장
  • 팀 간 협의: 호출 원천·목적지·포트, X-Service-Key 인증, ERP 조회·쓰기 API의 허용 범위 공유

주문 서비스와 ERP 자체 구현은 각 팀원이 맡고, 물류 측에서는 연결 경로와 WMS API 제공 범위를 맞췄습니다.

03. 무엇을 나누고, 왜 나눴는가

센터 3-Tier / DC Spine–Leaf

사용자 단말을 수용하는 센터는 Core–Distribution–Access로 역할을 구분했습니다. 서버 중심의 DC는 서비스별 Leaf를 두어 확장 위치와 연결 관계를 명확하게 했습니다.

WEB·WAS·DB 분리

웹 요청 수신, 물류 업무 처리, 데이터 저장을 구분해 접근 정책과 장애 점검 범위를 좁혔습니다. 외부 연동의 진입점은 WEB으로 통일했습니다.

업무망과 관리망 분리

서비스 API 경로와 SSH·운영 관리 경로를 분리했습니다. 관리 PC·JUMP를 별도 영역에 두어 관리 접근의 출발점을 구분했습니다.

차단·탐지·기록의 역할 분리

pfSense는 구역 간 통신 정책과 VPN, IPS는 인라인 검사, IDS는 복사 트래픽 관찰, WAF는 웹 요청 보호, rsyslog는 중앙 기록 수집을 맡도록 배치했습니다.

호출 주체별 API 키

서비스 DC와 ERP 키를 나눠 동일 서버에서도 호출 권한을 구분했습니다. ERP는 조회와 합의된 상품·주문 가져오기만 허용하고, 실물 출고 작업은 WMS 담당자 권한으로 분리했습니다.

대표 단말로 기능 확인

계획 인원을 VM으로 모두 복제하지 않고 대표 PC·VPCS로 VLAN·IP·게이트웨이 통신을 확인했습니다. 실습 자원을 업무 서버와 보안 구역에 우선 배분했습니다.

업무 데이터와 권한 설계

  • DB 트랜잭션과 상태 조건으로 예약·출고 처리 중 재고 정합성을 관리합니다.
  • 작업별 요청 키와 중복 삽입 방지 로직을 적용해 반복 요청에 따른 중복 처리를 제어합니다.
  • 서버 간 인증은 X-Service-Key를 사용하며, 키 값은 서버 환경 설정에서 관리합니다.

거점 간 네트워크와 업무 데이터 연결

본사 ERP, 서비스 DC, 물류 DC를 독립 거점으로 구분했습니다. VPN은 거점 사이의 통신 경로를 제공하고, API는 그 경로 위에서 전달하는 업무와 호출 권한을 정의합니다.

1. 본사 ERP → 물류 DC · IPsec VPN

네트워크 경로본사–물류 DC IPsec VPN · con2 · 양측 pfSense를 통한 내부망 연결
요청 원천·목적지본사 ERP-WEB 10.14.90.14 → 물류 WEB/WAF 10.20.20.10 TCP 80 → WMS
접근 정책ERP-WEB 단일 원천과 WEB 목적지·포트를 기준으로 방화벽·WEB 허용 범위를 협의했습니다. ICMP 응답과 TCP 80·HTTP 응답을 분리해 점검했습니다.
호출 인증X-Service-Key 헤더 · ERP_WMS_KEY에 대응하는 ERP 전용 키 · 키는 서버 환경 설정으로 관리
권한 경계/integration/v1 조회와 합의된 상품 동기화·주문 가져오기를 제공하고, 피킹·포장·실물 출고·반품 검수는 WMS 업무 권한으로 구분했습니다.

2. 서비스 DC → 물류 WMS · 재고와 주문 연동

쇼핑몰이 상품의 재고를 조회하고 주문 재고를 예약·해제하며 배송 상태를 가져오는 방향입니다. 물류 WEB을 진입점으로 두고 WMS에서 요청 주체와 재고 상태를 검사합니다.

업무요청물류 측 처리
SKU 재고GET /api/inventory/{sku}실물·예약·가용 재고 조회
주문 재고 예약POST /api/orders/reserve재고 예약과 주문 연결

인증에는 X-Service-Key와 물류 측 WMS_KEY에 대응하는 서비스 DC 전용 키를 사용합니다. ERP 키와 분리해 쇼핑몰 계약 경로에만 접근하도록 구성했습니다.

3. 물류 WMS → 서비스 DC · 주문 확인과 출고 승인

주문 가져오기GET /api/integration/v1/orders/{id} · 결제 완료 여부와 WMS 예약 상품·수량을 대조한 뒤 출고 작업에 등록

인증·예외X-Service-Key · WMS_SERVICE_KEY. 호출 시간 제한을 두고 연결 실패·시간 초과·상태 충돌을 구분해 처리합니다.

4. ERP 제공 API · 조회와 데이터 등록 분리

ERP 요청은 /integration/v1 아래 경로를 WMS 내부 업무 처리에 연결합니다. 조회 응답은 WMS DB의 현재 상태를 기준으로 반환하며, API 계약은 contracts/wms.openapi.json으로 공유하는 방식입니다.

  • 조회: 대시보드, 재고·창고·로케이션, 재고 이동, 예약·출고·반품 현황 등 ERP 조회 범위
  • 상품 동기화: POST /integration/v1/catalog · SKU 기준 상품명 등록·갱신 · 한 요청에 1~100개
  • 주문 가져오기: POST /integration/v1/shipments/import · orderId로 결제·예약 정보를 대조하고 기존 출고 행은 중복 생성하지 않음
  • 인증 응답: 키 누락·불일치는 HTTP 401, 응답 본문은 {"error":"SYSTEM_AUTH_REQUIRED"}. 유효한 키의 허용 범위를 벗어난 요청은 403으로 구분
연동 점검 순서: VPN·라우팅 → TCP 목적지 포트 → /health 응답 → 전용 키 인증 → 업무 조회 → 변경 요청. 물류 WEB의 /health 200 응답과 WMS 서비스 active 상태를 실제로 확인했습니다.

06. 증상에서 원인까지 좁혀 간 과정

사례 A · DNS를 바꿔도 패키지 서버에 접근하지 못함

증상: packages.wazuh.com 이름 해석 실패. DNS를 공용 주소로 바꿔도 동일했습니다.

확인: dig @1.1.1.1은 시간 초과, TCP 질의는 host unreachable. ip route get 1.1.1.1로 출구 경로를 확인하고, 외부 ping의 Destination Host Unreachable 응답과 대조했습니다.

원인: 기존 물류 WAN 경로는 실제 인터넷 라우터로 이어지지 않아 DNS 서버에 도달할 수 없었습니다.

조치·재시험: 설치용 NAT 어댑터와 DHCP 연결을 추가하고 경로 우선순위를 지정했습니다. 이후 이름 해석과 원격 HTTP 응답을 확인했습니다.

점검 기준: DNS 설정 변경 전에 DNS 서버까지의 경로와 도달 가능성을 먼저 확인합니다.

사례 B · VM에 추가한 두 번째 NIC가 보이지 않음

증상: VirtualBox에서 어댑터를 추가했지만 Linux의 ip -br link에는 enp0s3만 나타났습니다.

확인·원인: GNS3 노드 속성의 Adapters 값이 1인 것을 확인했습니다. VirtualBox 설정과 GNS3 노드 설정을 함께 맞춰야 했습니다.

조치·재시험: 노드를 종료하고 연결을 해제한 뒤 GNS3 어댑터 수를 2로 수정했습니다. 재기동 후 enp0s8 및 DHCP 주소 10.0.3.15가 나타났고 NAT 기본 경로를 확인했습니다.

점검 기준: 가상 NIC 변경 시 하이퍼바이저·GNS3·게스트 OS의 세 설정을 함께 대조합니다.

사례 C · 중앙 로그 설정 오류와 수신 확인

증상: rsyslog 설정 검사에서 객체 정의의 잘못된 문자 오류가 발생했습니다.

확인·조치: 오류가 가리킨 설정 파일의 문법을 수정하고 rsyslogd -N1로 설정 검사를 다시 수행한 뒤 서비스를 재시작했습니다.

재시험: TCP·UDP 514 리스닝을 확인하고 장비별 events.log에서 스위치 설정 변경 메시지와 pfSense IPsec 로그를 확인했습니다.

점검 기준: 설정 문법 → 프로세스 → 수신 포트 → 방화벽 → 실제 저장 파일 순서로 확인합니다.

프로젝트에서 익힌 점검 방식

연결 문제를 한 번에 설정 변경으로 해결하려 하지 않고, 인터페이스·경로·포트·HTTP 응답·로그를 나눠 확인하는 방식을 익혔습니다. 다른 담당자에게 요청할 때도 출발지, 목적지, 포트, 기대 응답을 함께 전달해 협의 범위를 구체화했습니다.
